# Testable specifications

On-demand capability, not progression. Main-session requests route through `.aidlc/system/skills/orchestration/aidlc/SKILL.md`; valid children follow `.aidlc/system/prompts/common.md`. Write only authorized run artifacts/evidence; return findings through the stage result, with no redispatch or state/approval/review writes.

- Read requirements, approved Intake, context and existing AC; separate behavior, design proposals, constraints and unknowns.
- Each stable AC ID needs actor/preconditions, action/inputs, observable outcome and verification method; cover applicable errors, boundaries, permissions and compatibility.
- Derive examples from real rules. Clarify business tradeoffs; never infer Oracles from code or generic assumptions.
- Check conflicts, omissions, observability and scope. Metrics need units, conditions and accessible evidence sources.
- Use current Spec/AC templates with pending decisions, assumptions and source mappings. Semantic AC changes need new approval even when IDs are unchanged.

Pre-installation advice is not a formal baseline. No product writes or human approval.
