# AIDLC · 单一工作入口

使用当前 AI 工具的文件、Git 和执行能力，无需另起 AI CLI 或安装运行器。安装内容应位于业务仓库的 `.aidlc/system/`；本 Skill 可以作为入口复制到工具支持的项目级 Skill 目录，但所有业务路径仍从项目根解析。

## 读取顺序

1. 确认业务仓库根目录。读取 `.aidlc/system/workflow/protocol.md`、`.aidlc/system/workflow/stages.json`、`.aidlc/config.json`；缺失时停止阶段执行，提示按 aidlc-agents 的 setup 指引接入。不要在错误目录或用户全局配置里自建替代安装。
2. 确认 work ID；存在多个候选而用户未指定时询问。读取该 work 的状态、原始需求、澄清记录及当前阶段所需批准快照。新需求按协议建立 work，并保留用户原话。
3. 读取 `.aidlc/system/prompts/common.md`，再加载当前阶段在 stages.json 中指定的角色、Prompt、模板与必要复用 Skill。不要一次载入全部角色。

## 路由与停止点

- 新需求/继续当前工作：按状态执行当前阶段，不凭用户提及“测试/发布”等词跳过批准依赖。
- 用户只问状态：报告当前阶段、最后有效批准、证据与下一步，不顺便实施或推进。
- 当前为 awaiting_approval：展示 work / stage / revision / review digest 及风险，等待决定，不重新生成相同 review 或自动启动下一阶段。
- 澄清答复：记录真实原话、来源及影响，继续被阻塞的阶段；答复不是批准。若影响已批准基线，按协议回退并使受影响下游状态失效。
- 明确批准具体当前 review：重新核对实际文件摘要与依赖，按协议记录人类真实决定。批准本身只使下一阶段可开始；仅当人类同时要求继续，才运行下一阶段，并再次停在 review。
- 拒绝/修改：保留既有快照与审批历史，建立新 revision；说明受影响下游产物，不原地改已批准文件，也不自动回滚业务代码。

## 不可混淆

阶段角色只写允许的产物；当前编排助手负责协议状态维护。只有 Implement 可按批准计划改业务代码/项目测试/构建配置。不可伪造人类批准、命令结果、SHA-256、Gate 或部署。无法真实计算摘要或执行必要验证时保持阻塞。

这是协作协议，不是认证/防篡改系统。一个人可以承担多个角色，但必须记录真实身份；AI 角色切换不是独立职责分离。每次交接报告已证明的边界，不能把发布就绪叫上线成功。
